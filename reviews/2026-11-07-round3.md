## HIGH

### 1. m-reviewer output contract cannot be parsed by m-review's own classifier
- Location: `agents/m-reviewer.md` (Output contract: `### 1. [HIGH] title / Location: / Status: confirmed|unconfirmed`); `skills/m-review/SKILL.md` step 5 and Harness notes; `skills/m-review/scripts/split-findings.mjs:9-11`.
- Problem: m-review step 5 requires lines `FINDING path:line | problem | scenario`, `REPRO cmd -> output`, `CLEARED path:line | reason` and runs the classifier on the report. The agent that m-review names as its matching agent emits none of those lines, no per-axis verdicts (Intent/Standards), no Cleared list, no consumer census, no refuter step. Its verdict rule ("no confirmed finding at MEDIUM or above") also differs from the skill's ("no confirmed in-scope finding and no axis `issues`").
- Failure scenario: the caller spawns `mstack:m-reviewer` and feeds its report to `split-findings.mjs`. `FINDING_RE` matches nothing, so the classifier sees zero findings (same silent-drop class as round-2 #3) and the merged review ends APPROVE with the defects in prose only. Separately, a confirmed LOW finding makes the skill say REQUEST CHANGES and the agent say APPROVE.
- Fix: make the agent's contract the skill's literal format (`FINDING ...`, `REPRO ... -> ...`, `CLEARED ...`, axis lines, last-line verdict) and take the approve rule from m-review verbatim; or state in the skill that the agent is a free-text drafter whose output the caller converts. One definition, not two.

### 2. m-critic output contract does not match what m-plan consumes; its verdicts have no branch in m-plan
- Location: `agents/m-critic.md` (Output contract; Constraints "Two rounds"); `skills/m-plan/SKILL.md` step 8, Iron Law, Gate function, Harness notes; `skills/m-plan/references/critic.md` (four blocks: Assumptions VERIFIED/REASONABLE/FRAGILE, Shape, Pre-mortem with exactly 3 scenarios, Findings Critical/Important/Note).
- Problem: m-plan's Gate demands "the critic's four blocks pasted or linked". The agent returns `Verdict: APPROVE|REVISE|REJECT`, Premise, Findings `[CRITICAL|MAJOR|MINOR]`, Predicted risks, Open questions: no assumption ratings, no shape choice, no 3-scenario pre-mortem, different severity names. REVISE means "fix and resubmit" while m-plan's Iron Law says a second critic round "is not allowed"; REJECT has no branch in m-plan. The agent caps at two rounds, m-plan at one pass.
- Failure scenario: m-plan spawns `mstack:m-critic` as its Harness notes say. The return has no pre-mortem, so step 8 ("turn any unmapped pre-mortem scenario into a task") has nothing to map; or the agent returns REVISE and the planner either breaks the Iron Law by resubmitting or ignores the verdict.
- Fix: make m-critic's contract the four blocks of `critic.md` (add a verdict line only if m-plan says what REVISE and REJECT do under the one-pass rule). Align severity names and the round cap (1) in both places.

### 3. `mola run` infers the task kind from keywords and silently uses it to select the policy row (permission profile, approval, route)
- Location: `cli/packages/plugins/cmd-run/src/routing.ts:125-144` (`KIND_RULES`, `inferKind`); `cmd-run/src/index.ts` (`taskKind: flags.kind || table ? policyKindOf(routingKind) : DEFAULT_TASK_KIND`, then `policyRow`).
- Problem: any prompt now selects `policy.routes.byTaskKind[policyKindOf(kind)]`, which carries `permissionProfile`, `approval`, `route`. Probed against the shipped table:
  - "Implement the design in spec.md" -> `plan`
  - "Translate this Python module to Rust" -> `zh-writing` (policy kind `chat`)
  - "Delete the docker image cache script" -> `vision`
  - "add UI test for login" -> `frontend` (the `test` rule sits after it)
  - "verify the build passes then refactor parser" -> `review`
- Failure scenario: a user whose policy gives `plan`/`review` rows a `read-only` profile runs "implement the design in spec.md"; the agent starts read-only and cannot do the task. Or a code translation runs under the `chat` row. Nothing tells the user the kind was guessed or that it changed the permission profile.
- Fix: infer only the model route; keep the permission/approval row on `DEFAULT_TASK_KIND` unless `--kind` or a skill command named the kind. Print "inferred kind: X" in the human note. Tighten the regexes (`image`, `design`, `spec`, `translate` are too broad) and put `test` before `frontend`.

### 4. Read-only agents are only partly read-only
- Location: `agents/m-explorer.md`, `m-verifier.md`, `m-reviewer.md`, `m-critic.md` (`disallowedTools: Write, Edit`); `agents/m-researcher.md` (`disallowedTools: Edit` only).
- Problem: `NotebookEdit` is not denied, so a `.ipynb` can be edited. Bash stays open, so `>`, `sed -i`, `git checkout` can write; only prose forbids it (m-explorer: "do not work around with shell redirection"; m-reviewer: "never to modify the tree"). m-researcher "writes only its report file" is unenforced: Write is allowed anywhere. m-review Harness notes admit "Bash is not in the deny list", yet section 12.2 and the descriptions say read-only.
- Failure scenario: a prompt-injected page or a confused reviewer rewrites a file; nothing blocks it.
- Fix: add `NotebookEdit` to every read-only deny list. Say in the bodies and section 12.2 that read-only means no edit tools and that shell writes are prose-only; for m-researcher put the report path in the prompt and note that Write is not denied.

### 7. Prompt adapter can contradict or mangle the user prompt
- Location: `cli/packages/plugins/cmd-run/src/routing.ts:231-264` (`OUTPUT_NOTE`, `ALREADY_WRAPPED`, `adaptPrompt`).
- Problem (probed):
  - Claude routes always get an `<output>Keep the answer short...</output>` block appended; a prompt saying "write a 2000 word report" is sent with a contradicting length instruction. `group/*` routes always get "Finish with: what changed, how it was checked...", wrong for a translation or a plain question.
  - `ALREADY_WRAPPED` only recognises `<task>` and `## Task`. A `<goal>..</goal><scope>..</scope>` brief is wrapped again in `<task>`; a `## GOAL / ## SCOPE` brief becomes `## Task` followed by `## GOAL` (heading levels inverted).
  - The body is not escaped: a literal `</task>` inside a pasted file closes the wrapper early.
  - The notes are hardcoded in TS. The JSON `families[*].rules` and the text in `model-routing.md` are never read, so the shared file changes only `style`; the gemini rule (constraints first, task last) is not implemented at all.
- Failure scenario: `mola run "Write a long design doc"` on a claude route is told to be short; a brief built from the m-dispatch template is double-wrapped.
- Fix: do not append an output instruction when the prompt already states a length or format (or move the note text into the JSON and make it opt-in); pass an already-structured prompt through unchanged; skip wrapping if the body contains the closing delimiter.

### 8. The ladder drops configured alternates, and a policy row silently outranks the picks
- Location: `cmd-run/src/index.ts` (`runLadder` option `alternates`; `...(routing?.plan ? { alternates: routing.ladder } : {})`; `primaryRoute = flags.route ?? policyRow ?? plan?.route ?? ...`).
- Problem: whenever a plan exists, `policy.fallback.alternateRoutes` is ignored, even when `routing.ladder` is empty (one pick survived the whitelist). Separately, `policy.routes.byTaskKind[kind].route` (the sample policy in `policy.ts` has one for `implement`) wins over `tasks[kind].picks`, so section 12.3 "mola run chooses the route from tasks[kind].picks" is false for any user with policy rows, and `decision.json` does not record which source won.
- Failure scenario: quota failure on the only surviving pick; `ladder` is `[]`, so `alternates` is `[]` and the run reports exhausted although `alternateRoutes: ["auto/kimi-k3"]` was configured.
- Fix: `alternates = dedupe([...routing.ladder, ...policy alternates])`; record `routeSource: flag|policy|picks|default` in decision.json; correct the 12.3 wording.

### 11. m-goal minimum-rounds rule is unenforced and cheap to satisfy
- Location: `skills/m-goal/SKILL.md` (Iron Law; Gate row "loop may stop"); `skills/m-goal/references/goal-file-format.md` ("rounds counts record calls"); `skills/m-goal/scripts/goal-state.mjs` (no check on `--status done`; a grep for "min" finds only the budget clamp at line 110).
- Problem: `rounds` increments on every `record` call, failing ones included, and the script accepts `--status done` at rounds 0. The Iron Law relies on the agent reading `rounds`, which is the discipline failure it exists to stop. A one-sub-goal task (default min 3) is told to run another verification round with no definition beyond another `record`.
- Failure scenario: an agent records two no-op checkpoints to reach 3, or ends `done` at 1 round; the script prints `ok`.
- Fix: add `--min-rounds N` to `init`, store it in state, and make `record --status done` exit 1 while `rounds < min`; define a round as a completed verify pass.
