## HIGH

### 1. Every shown script command is a repo-relative path that does not exist in a user project
- Files: skills/m-goal/SKILL.md:21; skills/m-verify/SKILL.md:21; skills/m-review/SKILL.md:31; skills/m-dispatch/SKILL.md:31; skills/m-guard/SKILL.md:29; skills/m-guard/references/hooks.md:22; skills/m-verify/references/verify-gates.md:91; skills/m-review/references/review-template.md:29
- Problem: all say `node skills/m-xxx/scripts/foo.mjs`. That path only resolves inside the mstack repo. When mstack is installed as a plugin (or under ~/.dsh/skills, ~/.codex/skills) the cwd is the user project, so the command fails with MODULE_NOT_FOUND. Only m-qa (SKILL.md:25) admits this, in one sentence, and gives no resolvable path either.
- Failure scenario: user runs m-goal in molamaker-site; step 4 `node skills/m-goal/scripts/goal-state.mjs ...` fails; the agent skips the state file, so the 3-strike / 90% / 100% rules "enforced by the script" become memory-only. Same for diff-blockers (the section 11 "mechanical scan"), split-findings and cluster-diffs.
- Fix: tell the agent to resolve the script relative to the SKILL.md it loaded (in Claude Code `${CLAUDE_PLUGIN_ROOT}/skills/m-goal/scripts/`), and state the fallback if the file cannot be found (do the check by hand and say so in the report). Use one wording in all skills.

### 2. diff-blockers.mjs reports OK on an empty diff and ignores untracked files (false-green gate)
- File: skills/m-verify/scripts/diff-blockers.mjs:24-26, 59-61; SKILL.md:21 ("no argument = your uncommitted changes").
- Problem A: default base is HEAD. m-plan step 3 (SKILL.md:19) ends every task with "commit", and m-dispatch worktrees commit. After that `git diff HEAD` is empty and the script prints "OK - no blockers" with exit 0 without having scanned anything. Problem B: `git diff HEAD` never lists untracked files, so a new test file is never scanned.
- Reproduced in a scratch repo: untracked `new.test.js` containing `it.only("x")` -> OK, exit 0. After `git add -A && git commit` the same content -> OK, exit 0.
- Failure scenario: the agent adds `describe.skip(` in a new spec file (or commits it), runs the scan, gets exit 0, claims done. This is the exact fake-completion case section 11.1 says the scan must stop.
- Fix: exit 2 (or print a loud "scanned 0 added lines") when the diff is empty; include untracked files (`git ls-files --others --exclude-standard`, scanned as all-added); default the base to `git merge-base HEAD <default-branch>` when HEAD is clean; have SKILL.md say how to pick the base.

### 3. m-review scope classifier drops every finding in a new (untracked) file
- Files: skills/m-review/SKILL.md:27 vs :31; references/review-template.md:51; scripts/split-findings.mjs (lineInScope).
- Problem: step 1 defines the scope as `git diff` plus untracked files, but step 5 feeds `<diff>` to split-findings. `git diff` contains no untracked file, so the file lookup is undefined, inScope=false, and the finding leaves the conclusion ("Confirmed but outside the diff -> drop it").
- Reproduced: scratch repo, new file `newfile.js`, `git diff > d.patch` (0 bytes), FINDING newfile.js:1 + REPRO -> conclusion 0, outOfScope 1. This very round (mostly untracked files) would lose all findings.
- Fix: state in SKILL.md and the template how to build the diff (`git add -N .` then `git diff <base>`), and make the script exit 2 when `--diff` is empty instead of silently classing everything out of scope.

### 4. The "clean checkout" recipe checks out HEAD, so it does not contain the change being verified
- Files: skills/m-verify/references/verify-gates.md:79-85; SKILL.md:22 and :47 ("git worktree add of the current HEAD").
- Problem: final acceptance runs in a worktree at HEAD. m-verify runs before the commit ("before committing, before a PR"), so the change is not in HEAD and the suite runs on the OLD code. The text says to run in a clean checkout "not only in your workspace" but never says how the change gets there.
- Failure scenario: the agent fixes a bug, leaves it uncommitted, runs the "clean checkout" suite, sees green (old code), and reports VERIFIED with a fresh-looking command.
- Fix: say explicitly: commit to a temp branch, or apply `git diff <base>` plus untracked files onto the fresh worktree, then run the suite and confirm `git -C <wt> diff --stat` equals the change under test.

### 5. Anti-cheat gate contradicts the regression-test rule next to it
- Files: skills/m-verify/SKILL.md:22, verify-gates.md:76 vs skills/m-debug/SKILL.md:29, :44; skills/m-plan/SKILL.md:19; m-verify SKILL.md:23.
- Problem: m-verify fails the task whenever the diff "touches tests, fixtures, conftest, graders" and "the user did not ask for that". m-debug requires a new regression test for every fix, m-plan makes "write failing test" the first step of every task, and m-verify step 5 itself requires new or modified checks. The "user asked" exception is not defined to cover these. FRAMEWORK 11.1 has the same ambiguity, so the skills had to resolve it and did not.
- Failure scenario: m-debug fixes a bug and adds the required `user.test.ts` case; m-verify step 4(a) says "the task FAILS; revert and re-verify". The agent deletes the regression test or ignores the gate.
- Fix: scope the gate to modified or deleted existing tests/fixtures/graders/CI and to config that changes pass criteria; treat purely added test files as allowed when the plan or debug report names them; keep "agent-created conftest/sitecustomize" as the hard FAIL.

## MEDIUM

### 6. The baseline gate cannot be reached in any documented flow
- Files: skills/m-verify/SKILL.md:20, verify-gates.md:54 ("Write it before your first edit"); no other SKILL.md mentions baseline.
- Problem: m-verify is invoked at the end ("before any success claim"). Nothing in m-start, m-plan, m-goal, m-dispatch or m-debug tells anyone to save `.mstack/verify/baseline.txt` before editing.
- Failure scenario: repo has 3 pre-existing red tests; the agent edits, then runs m-verify; no baseline file, so "every failure counts as new" and the task is blocked forever (the problem the gate was meant to remove), or the agent writes the baseline after its edits and bakes in its own failures.
- Fix: add one step to m-plan (first task), m-goal step 1 and m-debug step 2: "run the suite once and write the baseline (m-verify, references/verify-gates.md)". Or let m-verify step 2 rebuild the baseline from a worktree at the base ref when the file is absent.

### 7. m-goal final gate depends on a "rejected review" that m-review never produces, and m-review says it never gates
- Files: skills/m-goal/SKILL.md:23, :42; skills/m-review/SKILL.md:9 ("advisory: they inform, never gate"), :38-47.
- Problem: m-review output is per-axis pass/issues/not-assessed/not-applicable plus counts; there is no approve/reject verdict and no rule for when verdicts add up to "rejected". m-goal needs one ("never marked done with review findings open").
- Failure scenario: review returns `intent: issues`, one Unconfirmed finding, zero confirmed. m-goal cannot tell whether to append a sub-goal; two agents decide differently, and the `gate` line for m-review ("pass or fail") has no defined source.
- Fix: define in m-goal (the gate owner): m-review passes iff there is no confirmed in-scope finding and no axis `issues`; Unconfirmed/Cleared do not block. Reword m-review:9 to "does not edit or merge; the caller decides (see m-goal)".

### 8. m-start stale / abnormal-interruption detection uses fields that do not exist
- Files: skills/m-start/SKILL.md:18; skills/m-goal/references/goal-file-format.md:7-32; skills/m-team/references/team-config-template.md.
- Problem: (a) "no `## Closeout` at all counts as abnormally interrupted" - but the skeleton (m-goal step 1) creates `## Closeout` with a placeholder at creation, so the heading is always present; the real signal is "Closeout has no `status:`". (b) "status is not terminal" - a goal file has no status field until closeout, and team files (`v<N>.md`) have none at all. (c) "together with its resume-hint" - resume-hint exists only inside a written Closeout, i.e. never for an interrupted goal.
- Fix: say "Closeout section contains no `status:` line", derive the resume hint from the last checkpoint row plus `state.json`, and for team dirs use the last `v<N>.md` without a filled round-close block.

### 9. goal-state counts failures cumulatively (contradicting "3 in a row"); budget numbers have no measurable source
- Files: skills/m-goal/scripts/goal-state.mjs:41, 61; references/goal-file-format.md:57; principle 9 in m-start/SKILL.md:34 and FRAMEWORK section 4.
- Problem: failures[sig] is only incremented; `--progress` does not reset it. The same flaky signature seen three times across a day, with passes between, hits `stop`, while principle 9 and m-guard/m-verify/m-qa say "3 in a row". `--tokens` and `--budget` are numbers the agent must invent (no harness tool reports consumed tokens) and nothing invokes the script, so "stops the loop" is prose. An unreadable state file silently resets all counters (only a note in the output).
- Fix: pick one rule and make all skills match (cumulative is defensible if stated); reset failures[sig] on `--progress` if "consecutive" is intended; say budget % is the agent estimate against the cap declared in the goal file; refuse to overwrite an unparsable state file.

### 10. m-guard freeze hook can block the mandatory m-goal closeout
- Files: skills/m-guard/SKILL.md:23, references/hooks.md:17 and :31, scripts/check-pretool.mjs (freezeReason); skills/m-goal/SKILL.md:24.
- Problem: with `.mstack/freeze` active, every Edit/Write outside the listed prefixes returns `ask`. `.mstack/goals/<slug>.md`, `handoff.md`, `reviews/` are outside any typical prefix (e.g. `src/api`), and SKILL.md never says to add `.mstack` to the freeze list. hooks.md:17 states that in unattended `claude -p` an unanswered `ask` is treated as a denial.
- Failure scenario: overnight m-goal run under freeze; checkpoint and closeout writes are denied, so the run ends without a closeout - the failure FRAMEWORK section 1 says m-goal exists to prevent.
- Fix: always exempt `.mstack/` in freezeReason and say so in SKILL.md step 2 and hooks.md.

### 11. Eval cases may score nothing under the default ablation; AGENTS.md command does not account for it
- Files: evals/*/case.yaml (every grader has `arm: with-only`); AGENTS.md:9; `claude plugin eval --help` ("under with-without, graders marked with-only, incl. tool_used: Skill, are a plugin-fired indicator rather than part of the score").
- Problem: each case has only with-only tool_used graders, and the documented command uses the default `--ablation with-without`. Per the help text those graders are not part of the score, so `--threshold 0.8` may pass (or be undefined) regardless of routing. Not verified by a paid run; confidence medium.
- Fix: run one case (`--case route-continue-to-m-start --max-cost-usd 0.3`) with and without `--ablation none` and read the scored result; if with-only graders are excluded, add `--ablation none` to AGENTS.md:9 or add a scored grader (regex on the final answer, or llm).
